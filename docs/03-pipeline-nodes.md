# 流水线与节点合同

所有节点使用同一执行器。节点只接收冻结输入和受限依赖，返回类型明确的结果；不嵌套调用其他任务 handler，不自己创建线程或提交跨节点事务。执行器统一处理 checkpoint、取消、租约、日志、trace 和有限重试。

## 主链

| 节点 | 输入 | 持久输出 | 主要实现 |
|---|---|---|---|
| N0 接收与冻结 | 招标原件、固定公司版本、补充资料、制作配置 | InputManifest | 流式上传、类型/大小校验、hash、不可变版本 |
| N1 读取文档 | InputManifest | ParsedDocument + CoverageLedger | 原生解析、按页 OCR、表格/图片识别、来源定位 |
| N2 提取制作要求 | ParsedDocument | Requirements | 分窗结构化提取、引用校验、合并去重、覆盖检查 |
| N3 制定编写计划 | Requirements + 公司资料快照 | BidPlan | 资料召回/资格过滤、自动目录、响应分配、缺项判断 |
| N4 编写章节 | BidPlan + 允许使用的资料片段 | DraftSections | 规则填表、事实拼装、有界模型方案写作 |
| N5 核对与装配 | DraftSections + 原件附件 | DocumentPackage + Issues | 覆盖/事实校验、有限修复、表格和证明附件装配 |
| N6 渲染与发布 | DocumentPackage + Issues | DOCX + 待补清单 + ResultManifest | 确定性渲染、文件检查、原子发布 |

公司资料入库是独立的准备任务，复用 N1 的解析适配器，产生资料文本、事实候选和检索索引。公司资料任务不自动改动正在制作的快照。

## 通用产物合同

每个产物记录 `schema_version、producer_version、input_hash、output_hash、run_id、node_attempt_id、source_refs`。上游输出只读；所有改变产生新产物。JSON 是主要中间格式，原文和二进制附件用受控文件引用。

节点结果分为 `ok、ok_with_issues、failed`。业务缺项写入 Issues；技术失败写稳定 error_code 和受限错误摘要。成功记录必须对应已校验、完整写入的产物。单纯存在一个 JSON 文件或模型返回 200 不是成功。

执行器提交节点成功时同步提交下一个节点游标；模型/OCR 请求不在数据库长事务内。失败仅重试受影响的页、窗口或章节。每个内部单元也有稳定 unit_id、输入 hash、尝试记录和已完成产物引用。

## N0 接收与冻结

上传文件先暂存、校验实际格式和 hash，再发布不可变原件。上传成功与生成入队分开，刷新和重复提交通过幂等键返回同一任务。冻结档案、材料版本清单、模板、模型、提示词和节点版本。

拒绝路径穿越、伪装扩展名、超限、加密或损坏输入；文件名只用于展示，存储键由服务端生成。下载与引用始终检查所属项目、run 和当前用户的读取权限。项目归属由登录用户确定，生成及子 run 继承归属，不能由请求参数指定其他用户。

项目补充的价格、指定人员、日期等作为有来源的显式输入；公司名称等固定字段直接取公司档案，不交给模型选择或核对主体。N0 的重跑需要一个新输入清单和新 run，不能改写旧上传版本。本人项目补充资料不进入其他成员任务的输入。

## N1 读取文档

先读取 PDF/DOCX 原生内容，对扫描页或低可信区域调用 OCR。无需 OCR 的文件直接完成该内部步骤，不向 Provider 发送空页任务。OCR 不能改变来源页身份。

规范输出保留段落、标题、表格、图片引用、顺序、来源类型、原文和定位。PDF 记录页码/区域；DOCX 用段落、表格/单元格、对象定位，不编造分页号。页眉、页脚、文本框、嵌图及无法解释的对象计入覆盖账本。

覆盖账本逐页/逐块区分已读取、无正文、待 OCR、失败和未支持对象。关键内容不可读时停住；允许忽略的装饰性内容须有规则与记录。OCR 返回数量不等于覆盖正确；请求页身份、结果页身份和缺页清单都要核对。

首版一个主解析器加一个 OCR 适配器。对复杂表格先验证读取顺序和单元格对应，再扩大支持范围；不为名义上“支持所有格式”引入多套黑箱回退。

## N2 提取制作要求

按章节和上下文容量分窗，保留全文件窗口账本。输出至少包括：requirement_id、原文定位/引文、类别、强制性、所需响应、指定格式/附件、判断置信及未决问题。

类别至少区分公司资格事实、技术方案、商业/价格输入、固定表格、程序事项、无需正文的说明。引文必须能在对应来源定位，歧义不能被模型自行消除。合并重复要求时保留全部来源，不能合并掉金额、否定条件或例外。

正文生成不必等待人工逐条批准。内部状态是“已提取并校验”，不是“人工确认”。关键窗口失败或截断时不能以 partial_failure 冒充完整提取；只重试失败窗口，仍无法读取则停止并显示确切缺口。

模型仅输出结构化候选，不自行调用工具。超时/限流有界退避；schema 修复次数有限；凭据和权限错误不靠重复调用解决。

## N3 制定编写计划

一个 BidPlan 同时表达目录、各章响应的要求、章节类型、可用事实、参考片段、附件位置与缺项。匹配、证据和响应计划保留业务含义，但不各自建一套审批生命周期。

检索范围为固定公司公共资料库与当前项目的补充资料，不做公司主体筛选。按资料类型、人员或证明对象、证书类别和有效期等本次要求过滤，再使用关键词/语义召回，必要时有界模型选择。明确区分 `未检索/检索失败/无匹配/找到材料但不可用/可采用`，不能以系统错误证明“公司没有资料”。

相似度不能证明资格。证照有效期、所属人、证书等级等由结构化字段和原件核验。历史方案只提供参考方法，历史业绩事实不得顺带写入本项目。

公司证明的单页 OCR 失败可按显式冻结的 `failed_sources` 或 `failure_dispositions` 认证为独立待核处置，N3 读取结果记 `ok_with_issues`，原页单元及当前失败校验保持失败。失败文字不进入候选索引或事实；清单分别表达机器错误、来源模糊、独立确认的原文留空及目录缺项。该合同仅适用于公司证明的白名单读取/质量错误，不适用于关键招标读取、来源或检查点损坏、预算、凭据及诊断错误；无自动重试、付费补买或本地回退。

目录优先招标指定格式，再补公司模板。每条需响应要求至少有一个主要落点，允许其他章节交叉引用；每个附件有落点；禁止孤立要求、空章冒充覆盖及重复堆砌。

写作输入采用一种 schema，后续节点不再重新决定同一条要求属于哪个模式。目录结构在本节点内部校验并冻结，不产生在线确认任务。

## N4 编写章节

| 内容类型 | 生成办法 | 边界 |
|---|---|---|
| 公司基本字段/固定表格 | 程序按字段填充 | 未知字段用待补编号，禁止猜值 |
| 资质、人员、业绩 | 使用有来源的事实与原件 | 不能用模型推断替代证明 |
| 技术方案 | 要求 + 相关事实/参考片段 → 结构化章节内容 | 可提出拟实施方法，不虚构既有条件 |
| 商务与报价 | 已输入值、明确公式和源文格式 | 未输入报价不自动估算或承诺 |

统一输出 `heading、paragraph、list、table、image/attachment_ref` 文档块，附 requirement_refs 和事实来源。模型不能输出随意执行的 HTML/代码或控制任务流程。

每章保留实际请求、响应、校验及尝试引用；上下文按章节准备，不能每章重复塞整本招标文件。首版每 run 串行章节，跨 run 共用外部调用额度。成功章节有检查点；失败章节有限重试后可按已确认缺项策略转待补，不悄悄丢章。

## N5 核对与装配

程序先检查：要求落点、必需表格和附件、事实 ID、金额/单位/日期/人名一致性、缺失字段、附件可读性。每个事实来源须确实支撑对应断言，不仅检查引用 ID 存在。公司名称等由固定档案填充，不设置公司主体比对或核验步骤。

对高风险技术内容可作一次有界模型复核和定点修复，记录原文与修订；禁止无限审稿循环。不能支持的事实删除或改为待补；不通过的关键输入问题不能降格成普通提醒。

输出 Issues 清单包含严重度、节点、requirement_id、章节、原因和用户可执行的补充动作。区分“已写”“待补”“确实无需正文”；覆盖率不能把待补算成实质响应。技术文件整体失效时停止发布。

实际装配证明页、图片和表格。正文里的附件编号与实际附件一致。复制 DOCX 格式或重建 PDF 表格必须针对样本核验，不只检查提取到了文字。

## N6 渲染与发布

固定一种 DocumentPackage 结构，使用公司 DOCX 模板和受限渲染器。生成真正可编辑的正文/表格、标题层级、目录字段、页码、页眉页脚及可读附件。待补编号在正文和清单中保持一致。

清单展示层可将逐字相同的重复核对说明集中一次，但每次引用必须保留原位置、原始要求编号、来源及字符区间，能还原完整原原因；显示标题相同不允许合并不同要求。原文引用表格只有在冻结原件、引用范围、单元格文本与几何认证后恢复；组合引用逐片段验证并保留整体偏移，部分布局未恢复须在该片段明示，不能冒充读取成功或归为公司缺资料。原文、事实、任务及成功检查点不因展示优化改写。

渲染后检查 DOCX 包结构、必需章节、附件数量与 hash；发布之前完成渲染和文件存储。最终事务写入本 run 的结果清单、审计和 job 成功状态。下载仅读取已发布字节，不再次渲染。

每个 run 只能有一个有效结果包；同 run 重复完成只能幂等返回相同结果或明确拒绝。不同 run 没有共享的“当前文档指针”。取消、过期租约和旧 attempt 不能提交结果。

## 单节点调试

每个节点均支持从指定输入产物运行并输出本节点产物，不要求先启动全链 UI。诊断命令或 API 必须经过与全自动执行相同的 schema、权限、配额和 checkpoint 校验。

单步、恢复和退回重跑的版本规则见[日志与调试恢复](05-observability-and-debugging.md)。自动重试只针对技术瞬时失败；缺公司资料按产品规则留缺项，不重复请求模型试图“找出来”。
