3. 同一 renderer 有公司名常量（`:59`）、估算目录分支（`:755`）和多代文档分支。只借鉴中文字体/缩进、表格宽度、分页与附件可读性经验，不整体搬运。

## 对当前 M1 的具体调整

复核时暂停了仅增加 `WritingPart(part_id, title, guidance)` 的实现。随后独立实现的版本沿用旧 WritingTask 与响应单元的业务语义，映射到现有 `PreparedBid → DocumentPackage`，不增加第二套目录或通用编排层。具体代码与验证见 [M1 记录](07-m1-prototype.md)。

最小写作单元需要明确：稳定 ID、所属章节与顺序、响应操作、对应要求/事项、写作目的与 must_cover、允许事实/参考片段、禁止编造项、输出位置及完成判据。显示标题或数组位置不能作为复用身份。

同时记录 `format_status`（指定格式、已核对无指定、未读完、冲突）、模板/表格/单元格锚点与保护区。参考片段绑定版本/hash/定位及适用性，并记录改编去向；小标题是该单元的显示投影，不另建第二份编写事实源。

针对用户指定人工标书，先完成以下一条纵向链路，再进入 M2：

1. 对照招标要求选择有实质内容的人工技术段和记录表，保存来源位置、hash 与适用性。人工标书是质量基准；旧项目名称、历史价格、指定资源和签章不能自动成为本次输入。
2. 形成一个冻结编写计划，区分固定表填充、方法改编、真实附件与待补项。技术正文按检查对象、过程、异常授权和成果展开；不为增加页数堆砌章节。
3. 使用现有执行器实现并校验这些单元。写作内容、表格和附件共同进入 Word，缺项仍双向对应清单；内部调试文字保存在诊断产物，避免挤入正常技术正文。
4. 从参考文档提取 A4 页面、字体、标题、缩进、行距、表格和页码模式，记录采用项与有意差异。新文档逐页视觉检查，正文和表格保持可编辑。
5. 优先用已保存响应和本地预整理内容验证。确需验证真实生成质量时，仅调用需要改进的单元；新 prompt/输入/模型创建子 run，成功单元不得无依据重新付费。不能将手工/离线改编效果说成 DeepSeek 已自动达到相同质量。

## 2026-11-14 要点提取专项复核
